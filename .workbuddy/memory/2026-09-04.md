# 2026-09-04

## 架构评审（第二轮，更新 docs/architecture-review.md）

基于 `main` @ 1c0d0c5（含暂存区未提交的 MVC 重构）做了全量代码走查，重写了 `docs/architecture-review.md`。

**首版（8-30）问题处置**：H2 entrypoint 词分割、H3 TLS 硬约束、M1 WS 握手弱校验、M2 黑名单子串匹配、M6 批量下发原子性 —— 均已修复。**H1 同步 SQLite 阻塞事件循环仍未修**，仍是最核心瓶颈。

**本轮新发现的 4 个 P0**：

1. **自更新顺序 bug**（`agent/src/kk_agent/updater.py:195-200`）：`verify_and_replace()` 在 `_is_binary_target()` 之前执行，配合 `config.py:37` 的 `agent_bin` 缺省 = `sys.executable`。源码形态运行（`uv run kk-agent`，README 推荐的用法）且未设 `KK_AGENT_BIN` 时，下载的二进制会**覆盖容器里的 Python 解释器**。测试 `test_updater.py:87,101` 全部显式传了 `agent_bin`，该路径零覆盖。修复：改为先判 `sys.frozen` 再下载。
2. **命令回传不校验归属**（`hub.py:117-118` → `store.py:189`）：`append_result` 只按 id 匹配，不校验 pod，任一持 token 的 Agent 可污染其他 pod 的命令结果。
3. **命令 sent 状态断线即丢**：补发只查 `pending`（`store.py:181-183`），`sent/running` 要等 cleanup 满 1h 才标 lost，期间前端无超时反馈。
4. **Store 同步阻塞事件循环**（H1 延续）。

**P1 关键项**：`_CMD_COLS` 不含 `out` 但 `web/app.js:271` 读 `c.out` → **管理界面永远看不到命令输出**；`hourly` 表与 `lost` 状态命令永不清理（存储只增不减）；前端 5s 全量轮询 + 服务端逐行 `json.loads(last_metrics)`。

**结构性观察**：项目把全部资源优化投在 Agent 侧（RSS < 15MB），但千级容器规模下会先在服务端崩（同步 IO + 轮询放大）。

## 项目结构易错点（必记）

- `server/` 实际布局是 **`server/src/` 直铺**（包名靠 `server/pyproject.toml` 的 hatch `sources` 重映射为 `kk_server`），不是 `server/src/kk_server/`。
- **AGENTS.md 里写的 `server/src/kk_server/...` 是错路径**，README 写的 `server/kk-server/` 也是错的。三份文档三套路径，按 `server/src/` 为准。
- `agent/` 是 `src/kk_agent/` 嵌套，与 server 不对称。
- `server/Dockerfile` 用 `pip` 手装依赖并手工 `COPY src ./kk_server`，与 pyproject/uv.lock 脱节。
